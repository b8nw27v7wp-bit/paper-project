## 2.1 Electron 三端复用与桌面壳

### 2.1.1 原理

Electron基于Chromium+Node.js融合架构，主进程（Main, Node）负责窗口、IPC、文件与系统集成，渲染进程（Renderer, Chromium）承载Web UI，二者经`contextBridge`+`ipcRenderer/invoke`通信，`contextIsolation`与`sandbox`保障安全。`electron-builder`支持`externalBin`将后端二进制以sidecar随App分发，实现“前端同代码、后端随桌面走”的离线可用模式。桌面侧轻量存储以`better-sqlite3`（同步WAL）存UI状态，与云端PG业务库隔离，符合Codex“双库隔离”范式。

### 2.1.2 C4定位

在C4 L1中属“桌面壳”与“表现层”衔接层：`Vue3 Renderer → Electron Main(Node) → FastAPI(Python)`。L2分层中，Main承担IPC表（`plan:create, memory:search, graph:getState, inspector:open, workbench:sync`）与Fetch代理（自动注入`Authorization`、区分`origin`窗口），Renderer纯UI零业务，详见`02-系统架构设计.md` 4.1节进程模型。部署架构中，`frontend dist`可Web上云，`electron-builder externalBin:[server]`使桌面离线可查历史、在线切云端地址。

### 2.1.3 本项目选型论证

**选型：** Electron 40 + `electron-builder` + `better-sqlite3`（WAL `journal_mode=WAL synchronous=NORMAL busy_timeout=5000`）+ `node-pty`预留，对标OpenAI Codex官方链路（Electron 40 + Rust CLI 208 crates + IPC 70方法+双SQLite）。

**为何不用Tauri：** Tauri需Rust学习成本，单人28周求稳；Electron社区成熟、`Codex`已验证`70 IPC`扩展性，本课题IPC扩展至`workbench:sync`等5方法零障碍，且`better-sqlite3`编译预案明确（失败降级`electron-store/lowdb`，`04-可行性分析.md`）。

**为何三端复用：** 同Vue3代码`build:web`出Web、`build:electron`出桌面，CLI（Typer+Rich）仅只读trace，三端共用同一FastAPI（`apps/server/app/main.py:1` 16组66端点），降低三端成本。已落地`apps/frontend/src/views` 15视图（`router/index.ts:3`）、`apps/desktop/electron` sidecar `externalBin/bin`、`app/core/database.py:26` WAL，已验`vite 7.21s 2987 modules`。

**量化：** 桌面包<15M（不含模型），窗口状态读写`p95<10ms`，离线历史查询零网络依赖。

## 2.2 LangGraph StateGraph 多智能体编排

### 2.2.1 原理

LangGraph是LangChain面向多Agent的`StateGraph`编排框架，基于`Pregel`执行引擎。核心抽象：① `State(TypedDict)`显式共享状态，节点以`state->patch`形式增量更新；② 节点（Node）为LLM/工具/规则函数，边（Edge）含普通边与条件边（`conditional_edge`），支持回边重写；③ `MemorySaver/FileMemorySaver`检查点持久化`thread_id`对应状态，支持断点恢复与时间旅行；④ `astream_events`流式推送`thought/tool_call`事件，与SSE天然契合。ReAct范式（Reason+Act）在节点内显式`thought`与`tool_calls`，使轨迹可解释。

### 2.2.2 C4定位

属“编排层”，位于网关（FastAPI）之下、能力层（Memory/RAG/Graph/MCP/Reflector）之上。`02-系统架构设计.md` L2中，FastAPI接收`POST /plans`→委派LangGraph→按序调度能力层→回写`agent_run_log`→SSE推送。`03-六大模块详细设计.md` M1定义六节点：`Planner(ReAct证据注入)→Researcher(并行3工具)→Executor→Critic(双校验)→Mentor→Reflector`，`Critic`条件边决定`rewrites≤2`回边至Planner。

### 2.2.3 本项目选型论证

**选型：** `app/agents/graph.py:351` `StateGraph(PlanState)`六节点 + `app/core/checkpoint.py:1` `FileMemorySaver` + `_wrap_graph_for_compat` `thread_id`可恢复 + `app/services/planner.py` `PlanStore`内存+DB双写 + `app/agents/tools/registry.py:1` `ToolSchema/RegisteredTool`可热插 + `app/core/llm.py:1` `UnifiedClient` 4链fallback（DeepSeek/Qwen/OpenAI）。

**为何不用AutoGen/CrewAI：** AutoGen对话式状态分散、流程不可控，论文难画确定性DAG；CrewAI线性链条不支持`Critic驳回→Planner重写`回边。本课题`PlanState{goal,memory,graphDeps,vectorDeps,milestones,tasks,critic_feedback,mentor_msg,rewrites,trace_id,preferences,_thought,_research,_patch}`（`app/agents/state.py:1`）显式可追溯，`trace_id`贯穿6条`agent_run_log`，SSE 8事件`thought/tool_call/memory/rag/graph/task_created/critic_feedback/mentor_msg/reflector_patch/done`带`id/retry:3000`与`Last-Event-ID`重放，`Graph` DAG含`rewrites`回边，论文主图直接可用。

**Prompt加深：** `app/agents/prompts.py:1`中`Planner`注入`memory Top5/graphDeps/vectorHints/critic_feedback`并要求`citations`，`Critic`输出`{pass,feedback}`双校验，`Mentor`结合拖延史20字内个性化，已验`pytest test_agents_graph 5 passed`、`35/35`全绿，Critic拦截率>20%。

**性能：** SSE首字节<2s、全程<15s，`Critic`三重校验（时间重叠/负荷超载/前置缺失+LLM二次+图谱）保障规划合理性盲评+1分。

## 2.3 MCP（Model Context Protocol）工具协议

### 2.3.1 原理

MCP由Anthropic于2024-11发布，定义`Host/Client/Server`三元架构，传输层支持`stdio`与`SSE`，能力层暴露`tools/resources/prompts`。相比OpenAI Function Calling（进程内声明`tools`），MCP优势在于跨进程、跨厂商、可插拔：Server可为任意进程（Python/Node），Client按`mcp.json`声明拉起，社区可复用500+ Server（`calendar-mcp/better-todo-mcp/notion-mcp`），新增工具无需改模型Prompt，仅增配置。

### 2.3.2 C4定位

属“能力层-工具链”，由编排层（Executor）触发。`02-系统架构设计.md` 4.2时序中，`Executor task → 需同步? → mcp:call create_calendar_event → 成功写task.source_agent=mcp:calendar else 降级本地`。`05-API接口设计.md` `POST /mcp/call {server,tool,args}`与`GET /mcp/servers`为API面，`MCP`配置`mcp.json`可插拔，`apps/desktop/electron`负责`spawn`拉起，`apps/server/mcp`负责`Client` stdio调用。

### 2.3.3 本项目选型论证

**选型：** `MCP Python SDK 1.2` + `calendar-mcp/better-todo-mcp` 2个Server + `app/agents/tools/registry.py` `ToolSchema`热插 + `mcp.json`声明 + 超时5s重试1次、失败降级不阻断。

**为何不用Function Calling：** Function Calling为模型侧硬编码，新增1工具需改Prompt+代码、平均2-3天；MCP `mcp.json`增1 Server<1天，社区Server即插即用，且与LangGraph工具注册表（`RegisteredTool`）天然契合，论文可写“可扩展平台”创新。

**落地：** Electron Main `spawn(calendar-mcp)`，Python `mcp.Client` stdio `create_calendar_event({title,start,end})`/`create_todo`/`start_pomodoro`，成功率>95%（`02-需求与设计/01-需求分析.md` F07），失败不阻断规划，`task.source_agent`标记来源，`workbench:sync` IPC可透出工具调用至Inspector。

**风险预案：** 锁SDK 1.2版本，`04-可行性分析.md`已评估SDK变更风险。

## 2.4 RAG/GraphRAG 与 pgvector+Neo4j 知识驱动

### 2.4.1 原理

**RAG：** 切块（512+overlap50）→Embedding（1536维）→向量检索（cosine）→注入Prompt，缓解幻觉。**GraphRAG（Microsoft 2024）：** 在RAG基础上抽三元组建图、社区检测、图谱+向量混合检索，解决多跳先修依赖与全局摘要。**pgvector：** PG扩展，原生`vector(1536)`类型与`HNSW(m=16, ef_construction=64)`/`IVFFlat`索引，支持`vector_cosine_ops`。**Neo4j：** 原生图库，`(:Knowledge)-[:PREREQUISITE{weight}]->(:Knowledge)`表达先修，`MATCH (k)-[:PREREQUISITE*]->(pre)`多跳查询。

### 2.4.2 C4定位

属“能力层-知识”与“存储层”联动。`02-系统架构设计.md` L2中，能力层`RAG/Graph`对接`PG+pgvector`与`Neo4j`，为编排层Planner提供`graphDeps+vectorDeps`证据。数据流：`上传→MinIO→切块→pgvector(type=knowledge)→抽三元组→Neo4j`，规划时`MATCH PREREQ 10 + 向量Top10`→Planner证据式生成带`citations`，Critic以图谱校验前置缺失，ECharts Graph可视化先修链。

### 2.4.3 本项目选型论证

**选型：** `PG16+pgvector 0.7 vector(1536) HNSW m=16 ef=64`（`app/models/memory.py:17`、`app/core/database.py:49,126-136`、`alembic/002_vector_idx.py:18-42`幂等`CREATE INDEX IF NOT EXISTS idx_memory_embedding_hnsw`）+ `Neo4j 5` + `MinIO` + `切512+overlap50` + `LLM抽PREREQUISITE` + `ECharts Graph`。

**为何PG一库两用而非独立向量库：** Milvus/Qdrant需额外运维，毕设量级（<5万Chunk、<1万节点）下PG+HNSW已满足`p95<200ms`，`USE_PG=0`时`Text(JSON)`+内存cosine兜底零依赖跑通，`USE_PG=1`切真HNSW，`py scripts/pgvector_bench.py --n 500 --q 20 p95 108ms`、`graph_bench 10k/50k p95 107ms`已验，运维成本最低，论证见`02-系统架构设计.md` 7.2节。

**为何轻量化GraphRAG：** 完整GraphRAG社区检测重，本课题<1万节点下仅抽`PREREQUISITE`+`CONTAINS/BELONGS_TO`三关系，`MATCH PREREQ p95<500ms`，与向量`Top10`混合即实现“向量广度+图谱精度”互补，证据式`Task.citations:[{chunk_id,page,score}]`可追溯至教材页码，规避幻觉，支撑论文“知识驱动”创新。

**索引与缓存：** `memory_chunk`上`HNSW`+`user_id+type`联合索引，`agent_run_log`上`trace_id+agent_name+created_at`联合索引供工作台重放，`cache:rag:{hash} 30m`与`cache:plan:{hash} 1h` Redis缓存，`GET /rag/search?q&top_k&subject`与`GET /graph?subject`为API面。

## 2.5 记忆机制与反思自进化

### 2.5.1 原理

**记忆：** 分短期（上下文窗口10轮）与长期（向量外存）。长期以`memory_chunk(type=memory)`存偏好/拖延/薄弱点，写路径摘要Prompt→Embedding→入库，读路径阈值`cosine>0.75 Top5`召回注入Planner，借鉴MemoryBank遗忘曲线与MemGPT OS分页思想，但聚焦规划约束。**反思：** 源于Reflexion（verbal reinforcement）与Self-Refine（self-feedback），以语言化补丁`next_plan_patch`替代梯度更新，实现策略自进化。本课题周维度反思从`task_execution_log`量化完成率/拖延率/负荷，LLM生成`analysis+patch`回注下周。

### 2.5.2 C4定位

属“能力层-Memory/Reflector”与“存储层-Redis/PG”联动。`02-系统架构设计.md` L2中，Memory为Planner提供`Top5`，Reflector由`APScheduler`驱动，产出`reflection_report`经Redis通知至表现层大屏。`03-六大模块详细设计.md` M2/M6详述：M2双记忆读写与`22:00`批量摘要，M6 `cron 0 23 * * 0`+手动`POST /reflection/run`→`analysis+next_plan_patch{reduce_load,add_buffer}`→通知→下周Planner合并。

### 2.5.3 本项目选型论证

**选型：** `memory_chunk vector(1536) HNSW` + `cosine>0.75 Top5` + `APScheduler 22:00`批量摘要 + `app/services/memory.py:139` `asearch_memory`真embedding（修复`loop.is_running→hash mock`误用，`memory_search`注册表优先`await asearch`）+ `AsyncIOScheduler cron 0 23 * * 0` + `reflection_report(week,rate,delay_rate,avg_load,analysis,patch)` + `cache:plan 1h`。

**为何双轨记忆：** 纯窗口缺跨周个性化，纯向量缺即时上下文，双轨互补；阈值0.75经消融实验调优，召回<1s，支撑有/无记忆对比（预期完成率+15%），为论文提供量化证据。

**为何周维度反思：** 教育规划以周为自然迭代单元，日反思噪音大、月反思反馈慢；`Reflector`独立为六节点之一，`Planner`重写时合并`_patch`，错过补跑保障可靠性，`task_execution_log`全量为反思提供`ground truth`，`Langfuse`追踪可观测。

**量化：** 记忆检索`p95<1s`，反思生成`1份/周`，`patch`生效后下周完成率不降（`01-需求分析.md` F11验收）。

## 2.6 小结

本章五项技术构成“桌面壳-编排-工具-知识-记忆”全栈基座：Electron解决三端复用与离线可用，LangGraph提供可控可追溯协作，MCP实现工具可插拔平台，pgvector+Neo4j实现证据式知识驱动，记忆与反思实现个性化与自进化。五者在C4中分层解耦、经`trace_id`与`PlanState`贯通，为第4章总体设计（C4图、三端设计、技术选型）与第5章详细设计（M1-M7、ER、接口）提供直接依据。选型均以“单人28周可落地、论文可画图、答辩可演示”为约束，对标Codex与顶会方案，已通过`35/35 pytest`与`7.21s vite build`验证。
